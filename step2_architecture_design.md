# Шаг 2: Проектирование архитектуры

## 1. Задача

Определить структуру Python-кода для Streamlit-приложения, реализующего бэктестер ребалансировки. Архитектура должна быть простой, читаемой, модульной (в разумных пределах) и учитывать особенности Streamlit, включая необходимость кэширования.

## 2. Основные компоненты и поток данных

Приложение на Streamlit выполняется сверху вниз при каждом взаимодействии. Основные логические блоки:

1.  **Настройка UI (Боковая панель):**
    *   Сбор пользовательских вводов:
        *   Список тикеров (текстовое поле).
        *   Диапазон дат (выбор начала и конца).
        *   Частота ребалансировки (выпадающий список/радиокнопки).
        *   Целевые веса (динамически создаваемые поля ввода для каждого тикера + Cash). *Требует продуманной реализации для удобства и валидации суммы.*
        *   Безрисковая ставка (числовое поле ввода).
    *   Кнопка "Запустить расчет".

2.  **Обработка ввода и запуск расчетов (Основная область, после нажатия кнопки):**
    *   Валидация введенных данных (список тикеров, сумма весов).
    *   **Загрузка данных (`@st.cache_data`):** Функция для загрузки исторических цен (`yfinance`). Кэшируется по тикерам и датам.
    *   **Выполнение бэктеста (`@st.cache_data`):** Основная функция расчетов:
        *   Принимает на вход: данные цен, веса, частоту ребалансировки, начальный капитал (можно зафиксировать или добавить в UI).
        *   Рассчитывает:
            *   Даты ребалансировки.
            *   Ежедневную стоимость портфеля (ребалансировка и B&H).
        *   Возвращает: DataFrame с результатами (стоимость портфелей).
    *   **Расчет метрик (`@st.cache_data`):** Функция для расчета метрик (CAGR, Max Drawdown, Sharpe, Sortino, Recovery Factor) на основе DataFrame с результатами бэктеста и безрисковой ставки. Кэшируется по результатам бэктеста и ставке.

3.  **Отображение результатов (Основная область):**
    *   Отображение сообщений об ошибках (если валидация/загрузка/расчет не удались).
    *   **График цен активов:** Построение интерактивного графика нормализованных цен (Plotly) на основе загруженных данных. *Возможно, с переключателями видимости.*
    *   **График эквити:** Построение интерактивного графика (Plotly) сравнения стоимости ребалансируемого портфеля и B&H.
    *   **Таблица метрик:** Отображение рассчитанных метрик в виде таблицы (Streamlit `st.dataframe` или `st.metric`).

## 3. Альтернативы структуры кода

1.  **Все в одном файле (`app.py`):**
    *   *Описание:* Весь код (UI, загрузка, расчеты, графики) находится в одном Python-скрипте.
    *   *Плюсы:* Максимальная простота для небольшого проекта, легкость запуска.
    *   *Минусы:* С ростом сложности становится трудно читать и поддерживать. Функции могут стать слишком длинными. Повторное использование логики затруднено.
    *   *Оценка (Простота: 9, Читаемость: 6, Модульность: 4, Соответствие Streamlit: 8):* **27/40**

2.  **Разделение на функции в одном файле:**
    *   *Описание:* Код в одном файле (`app.py`), но логика разбита на четкие функции (например, `setup_sidebar`, `load_data`, `run_backtest`, `calculate_metrics`, `plot_equity`, `plot_prices`).
    *   *Плюсы:* Улучшает читаемость и структуру по сравнению с вариантом 1. Сохраняет простоту запуска. Хорошо подходит для Streamlit и кэширования.
    *   *Минусы:* Все еще один файл, который может разрастись.
    *   *Оценка (Простота: 8, Читаемость: 8, Модульность: 6, Соответствие Streamlit: 9):* **31/40**

3.  **Разделение на модули (например, `app.py`, `core.py`, `plots.py`):**
    *   *Описание:*
        *   `app.py`: Основной скрипт Streamlit, отвечает за UI и вызов функций из других модулей.
        *   `core.py`: Содержит функции для загрузки данных, выполнения бэктеста, расчета метрик (логика, не связанная с UI).
        *   `plots.py`: Содержит функции для генерации графиков Plotly.
    *   *Плюсы:* Лучшая модульность и организация кода. Облегчает чтение, тестирование и потенциальное повторное использование `core.py`.
    *   *Минусы:* Незначительно усложняет структуру проекта (несколько файлов). Требует корректного импорта между модулями.
    *   *Оценка (Простота: 7, Читаемость: 9, Модульность: 9, Соответствие Streamlit: 9):* **34/40**

## 4. Выбор архитектуры

Учитывая требования к простоте, но также желательность хорошей структуры и читаемости, **выбираем Альтернативу 3: Разделение на модули (`app.py`, `core.py`, `plots.py`).**

*   **`app.py`:** Отвечает за интерфейс Streamlit (боковая панель, основная область), сбор ввода, вызов функций из `core` и `plots`, отображение результатов (графики, таблицы, метрики).
*   **`core.py`:** Содержит "чистые" функции без привязки к Streamlit для:
    *   Загрузки данных (`load_price_data`) - с использованием `@st.cache_data` (декоратор будет в `app.py` при вызове или здесь?). *Лучше декоратор оставить в `app.py` при вызове функции из `core.py`, чтобы `core.py` не зависел от Streamlit.* - **Нет, декоратор должен быть у самой функции, чтобы кэширование работало корректно при импорте. `core.py` будет импортировать Streamlit только ради декоратора.**
    *   Выполнения бэктеста (`run_backtest`).
    *   Расчета метрик (`calculate_metrics`).
    *   Возможно, вспомогательные функции для расчетов.
*   **`plots.py`:** Содержит функции для создания фигур Plotly:
    *   `plot_normalized_prices`.
    *   `plot_equity_curves`.
    *   Функции принимают DataFrame'ы с данными и возвращают объекты `plotly.graph_objects.Figure`.

Эта структура обеспечивает хороший баланс между организацией кода и простотой, подходящей для Streamlit-приложения среднего размера. Она также позволяет легко применять кэширование к функциям в `core.py`.

## 5. Самокритика и доработка (Шаг 2)

**Оценка выбранной архитектуры: 9/10**

**Положительные стороны:**
*   Хорошая модульность: разделение UI, основной логики и графиков.
*   Улучшает читаемость и поддерживаемость по сравнению с одним файлом.
*   Позволяет легко применять кэширование Streamlit к основным вычислительным функциям в `core.py`.
*   Способствует потенциальному повторному использованию функций из `core.py`.

**Потенциальные риски и области для улучшения (почему не 10/10):**
1.  **Зависимость `core.py` от Streamlit:** Решение разместить декораторы `@st.cache_data` внутри `core.py` создает зависимость этого модуля от Streamlit. Хотя это необходимо для правильной работы кэширования при импорте, это делает `core.py` менее "чистым" и независимо используемым. *Это осознанный компромисс ради эффективности в рамках Streamlit-приложения.*
2.  **Обработка ввода весов:** В архитектуре упомянута "динамическая генерация полей ввода", но не детализирован механизм. Это ключевой элемент UI, и его реализация должна быть продумана на Шаге 3 (Промпт), чтобы избежать путаницы с ключами виджетов Streamlit и обеспечить корректную валидацию суммы весов.
3.  **Управление состоянием:** Неявно предполагается, что состояние (введенные параметры, результаты расчетов) будет управляться стандартным потоком Streamlit и кэшированием. Для более сложных взаимодействий могло бы потребоваться `st.session_state`, но для текущих требований это, вероятно, излишне.

**План доработки (Шаг 2):**
*   Доработка не требуется, архитектура утверждается.
*   Необходимо **особое внимание уделить реализации ввода весов** и **применению декораторов кэширования** в Шаге 3 (Промпт).
